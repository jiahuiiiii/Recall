# Eval fixtures

One YAML file per **scenario**.

## Sequence — read this first

- **Memos inside a file are ordered and the order is the test.** They run top to bottom
  against a person graph that starts **empty**. Memo 3 can only recognise someone if an
  earlier memo in the same file recorded them.
- **Files are independent.** Each scenario gets its own fresh graph; they never see each
  other. Cluster ids only need to be unique *within* one file.
- **Every repeat starts fresh too**, so runs never contaminate each other.

So a file is one continuous story from one person's life, in chronological order — not a
bag of unrelated memos.

**Prefer few long scenarios over many short ones.** Within a scenario, every person
already recorded is a candidate the resolver has to rule out, so one file with 12 people
is far harder — and far more realistic — than four files with 3. Aim for 3–5 scenarios of
6–12 memos.

## Check your work

```bash
uv run eval/check_fixtures.py     # free, never calls a model
```

It counts progress toward the targets and flags the mistakes that make a fixture score
meaninglessly: a person mentioned only once (nothing to link), an "ambiguous" mention
that carries a definite label, a scenario too short to test memory.

```yaml
id: reunion                     # unique, filename-safe
description: one line, what this scenario is testing

memos:
  - id: m1                      # unique within the scenario
    transcript: |
      Free text, exactly as a transcript would come out of Whisper.
      Messy. Filler words. Half-finished sentences. No tidying.
    mentions:
      - cluster: kang_ling      # GOLD cluster id — the same real human shares
                                # one cluster id across every memo in the file
        as: "Kang Ling"         # how they were referred to in THIS memo
        substantive: true       # false = passing mention, must NOT be recorded
        ambiguous: false        # true = a human could not resolve this from the
                                # memo alone; the system SHOULD ask about it
```

## Which situation goes in which file

Two kinds of scenario, with different jobs. Don't mix them.

### Diagnostics — small, isolated, one failure mode each

Three to four memos. Deliberately easy to reason about. When a number drops, these tell
you *which* capability broke. Keep them focused: one file, one thing being tested.

| File | Tests | Correct behaviour |
|---|---|---|
| `same_first_name.yaml` | **Precision.** Two different people share a first name. | Must NOT merge |
| `name_variants.yaml` | **Recall.** One person, many forms: "Wei Lin" / "Weilin" / "the GIC one" / "the quant lady". | Must merge, every time |
| `passing_mentions.yaml` | **The substantive filter.** People greeted, name-dropped, or mentioned as someone else's context. | Must NOT be recorded |

### Arcs — long, realistic, mixed

Six to twelve memos each, one continuous stretch of your life in chronological order.
**This is where the benchmark numbers come from.** Hard cases go *inside* an arc, not in
their own file, because that is how they occur — a re-encounter is only hard when there
are eleven other people it could have been.

| File | Setting |
|---|---|
| `arc_semester.yaml` | Uni over months — classmates, project teammates, people from CCAs, someone you meet twice and half-remember |
| `arc_conference.yaml` | A multi-day event — a burst of new people, then re-encounters on day 2 and 3 |
| `arc_worklife.yaml` | Professional networking across weeks — meetups, intros, people who change jobs |

**So:** writing a same-first-name case? If you are testing that behaviour in isolation, it
goes in the diagnostic file. If it is one of twelve things happening across a semester, it
goes in the arc. Do both — the diagnostic proves the mechanism, the arc proves it survives
contact with a real graph.

### Rough target

| | Files | Memos each | Total |
|---|---|---|---|
| Diagnostics | 3 | 3–4 | ~10 |
| Arcs | 3 | 6–12 | ~25 |

That lands around 35 memos, comfortably past the 20 where numbers stop being anecdotes.

## Rules for writing these

- **Hand-write them. You control the labels.** A fixture generated by the same model
  being tested proves nothing.
- **Write realistic input.** Singlish, code-switched Mandarin/Malay/English, dropped
  articles, self-corrections. Names sit exactly at code-switch boundaries, which is
  where transcription is worst — that is the case that matters.
- **`cluster` is ground truth, not a guess.** Two mentions share a cluster id if and
  only if they are the same human.
- **Include hard cases deliberately.** Same first name, different people. Same person,
  different name form ("Wei Lin" / "the GIC one" / "Weilin"). A person mentioned once
  and never again.
- **Mark `substantive: false`** for anyone only greeted or name-dropped. They must not
  reach the contact book.
- **Mark `ambiguous: true`** where a careful human genuinely could not decide. This is
  the band the EIG question exists to serve, and the count of these is the denominator
  for "questions per ambiguity resolved".

## Target

20–50 memos across scenarios. Below ~20 the numbers are anecdotes.
